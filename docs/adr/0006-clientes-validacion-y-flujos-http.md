# ADR-0006 — Clientes: validación y flujos HTTP

Fecha: 2026-10-21. Estado: aceptada para etapa 5. Cierra D-06 para clientes; productos/SKU siguen pendientes en etapa 6.

## Decisión

- Nombre requerido: trim, 1–180 caracteres Unicode. Correo opcional: trim/minúsculas, dirección simple válida sin nombre de presentación, hasta 254 bytes, sin consulta DNS ni unicidad añadida. Teléfono opcional: trim, hasta 40 caracteres Unicode, texto libre sin imponer formato nacional. Notas opcionales: CRLF/CR a LF, trim, hasta 5000 caracteres Unicode, conserva saltos internos y tabuladores. UTF-8 válido; rechazar controles en campos de una línea y controles distintos de LF/tab en notas. Campos opcionales vacíos se persisten como NULL. Estado obligatorio, solo active/inactive. No se aceptan actor, tenant, fechas ni ID de cliente desde el formulario como campos de la entidad.
- Formularios de clientes admiten hasta 64 KiB para soportar notas Unicode codificadas en URL; siguen usando sesión, CSRF y control de origen comunes. Otros formularios conservan 16 KiB. Validación 422 con errores por campo y valores conservados; no escribir parcialmente. SQL permanece parametrizado.
- GET `/app/customers` devuelve página completa o contenido del módulo para HTMX. GET `/app/customers/table` devuelve resultados/paginación para HTMX; navegación normal devuelve página completa. Filtros: search (trim, máximo 180 caracteres), status vacío/active/inactive; sort allowlisted created_desc (defecto), created_asc, name_asc, name_desc. Desempate estable por UUID en la misma dirección. Búsqueda literal por nombre/correo, escapando =, % y _; comparación con collation MySQL existente. Page por defecto 1, page_size 25, solo 10/25/50; offset máximo 100000. Parámetros inválidos: 422. Enlaces y URL del navegador conservan filtros/orden/tamaño; cambiar filtros reinicia página. Lista y conteo usan snapshot de lectura consistente, sin caché.
- GET/POST `/app/customers/new`, GET `/app/customers/{id}`, GET/POST `/app/customers/{id}/edit`, POST `/app/customers/{id}/delete` según arquitectura. Añadir GET `/{id}/delete` para confirmación accesible sin JavaScript; POST exige confirm=yes, además de permiso y CSRF. Baja lógica, sin restauración ni borrado físico en este MVP. Los IDs de recurso deben ser UUID v4 canónicos en minúsculas antes de consultar columnas ASCII; evita errores de conversión para rutas Unicode. Recurso ajeno, ausente, malformado o eliminado: mismo 404; acción prohibida: 403 antes de resolver el recurso.
- Owner/Admin crean/editan/dan de baja; Viewer solo consulta. Cada servicio resuelve permiso vigente desde MySQL. Mutaciones bloquean tenant antes de autorizar, coordinándose con cambios de membresía/estado; repositorios siempre filtran por tenant activo. No se acepta un rol de formulario/contexto antiguo. Edición sin cambios válida no produce falso 404.
- HTML normal: éxito POST con 303 a detalle o listado. HTMX: creación 201 con detalle y aviso, edición 200 con detalle y aviso, baja 200 con listado actualizado; HX-Push-Url actualiza URL canónica sin recarga completa. Errores de formulario devuelven el formulario con errores y etiquetas/IDs estables. No se introduce JavaScript de aplicación. Navegación parcial sustituye contenido del módulo; historyCacheSize=0 y no-store evitan reutilizar páginas sensibles entre empresas.
- Mutación y auditoría de éxito se confirman juntas. Acciones customers.create/update/delete, entidad customer, actor/tenant confiables e ID propio; sin PII ni valores editados. Denegaciones/validación no incluyen ID ajeno ni entradas de formulario. Fallo de auditoría revierte mutación. SSE se incorpora en etapa 7, no se introduce broker anticipado.

## Consecuencias

Sin migraciones ni dependencias nuevas. sqlc 1.31.1/MySQL deja sin expandir `sqlc.arg` dentro de `CASE WHEN ... IN (...)`; usar comparaciones `=`/`OR` verificadas en el SQL generado, sin cambiar la herramienta fijada. Vista específica de clientes con layout amplio; no se extrae todavía un framework de formularios/tablas ni componentes compartidos de recursos. Pruebas unitarias de normalización/límites/parsers, MySQL y HTTP normal/HTMX para CRUD/aislamiento/CSRF/roles/filtros/orden/paginación/auditoría, y revisión de teclado/escritorio/tablet. Rendimiento objetivo y comparación Filament siguen en etapa 8; se registra el trabajo de clientes como referencia para el segundo CRUD.
